## What this is

DumpDetective is a .NET 10 native-AOT CLI tool that analyzes Windows memory dumps (`.dmp` / `.mdmp`) via ClrMD (`Microsoft.Diagnostics.Runtime`) and `.nettrace`/`.etl` traces via TraceEvent. It runs dozens of analysis commands (heap stats, memory-leak detection, deadlock detection, GC fragmentation, CPU/allocation/GC trace analysis, etc.) and renders reports to HTML, Markdown, JSON, plain text, or compact binary.

Full command reference: `README.md` and `Docs/documentation.md`. Architecture deep-dive: `Docs/Architecture.md`. Test architecture: `Docs/Testing.md`. Plugin authoring: `Docs/Plugins.md`.

## Build, test, run

```bash
# Build (from repo root)
dotnet build DumpDetective.Tests/DumpDetective.Tests.csproj

# Self-contained AOT publish (single native exe: DumpDetective.Cli.exe)
dotnet publish DumpDetective.Cli -r win-x64 -c Release

# Run all tests
dotnet test DumpDetective.Tests

# Run one command's tests
dotnet test DumpDetective.Tests --filter "FullyQualifiedName~HeapStats"

# Verbose (shows Report_Summary per-command output)
dotnet test DumpDetective.Tests --logger "console;verbosity=detailed"

# Force regeneration of all cached scenario dumps (e.g. after editing DiagnosticScenarios)
$env:DD_REFRESH_DUMPS = "1"; dotnet test DumpDetective.Tests
```

Test suite covers every analysis command via scenario-based integration tests — each command gets its own isolated heap dump generated by the standalone `DumpDetective.DiagnosticScenarios` console app (spawned as a child process), cached under `%TEMP%\DumpDetective\Scenarios\`. First run is slow (dump generation per scenario); subsequent runs reuse cached dumps and complete in under a second unless the `DiagnosticScenarios.exe` binary is newer than the cache. See `Docs/Testing.md` for the full lifecycle and the steps to add a new command's test (scenario class + `DiagnosticScenarios` entry + `AllScenarios` registration + test class).

No lint/format command is defined in this repo beyond standard `dotnet build` warnings.

## Architecture

Multi-project solution (`DumpDetective.slnx`) with a strict, unidirectional dependency graph:

```
Cli ──────────────────────► Commands
 │                             │
 │                             ▼
 │                       Analysis.Memory / Analysis.Trace ──┐
 │                                                           │
 └──────────► Reporting ──────► Core ◄──────────────────────┘
```

- **`DumpDetective.Core`** — interfaces (`ICommand`, `IRenderSink`, `IHeapObjectConsumer`), models (`ReportDoc`, `Finding`, `ThresholdConfig`), `DumpContext`/`HeapSnapshot`, AOT JSON source-gen contexts. Depends on nothing else in the solution.
- **`DumpDetective.Analysis.Memory`** — ClrMD heap walk (`HeapWalker`), `DumpCollector`, BFS retained-size index/cache, all dump-side analyzers/consumers. Depends only on Core.
- **`DumpDetective.Analysis.Trace`** — TraceEvent-based trace analyzers, correlation engine (dump+trace cross-source rules), event classification/normalization. Depends only on Core.
- **`DumpDetective.Reporting`** — `IRenderSink` implementations (`HtmlSink`, `MarkdownSink`, `TextSink`, `ConsoleSink`, `JsonSink`, `BinSink`, `CaptureSink`), `ReportDocReplay`, `ReportDiffer`. Depends only on Core.
- **`DumpDetective.Commands`** — one `ICommand` implementation per CLI sub-command, split into `Memory/` and `Trace/`. Depends on Core + Analysis.Memory/Trace + Reporting.
- **`DumpDetective.Cli`** — AOT entry point, `CommandRegistry` (single source of truth mapping command name → `ICommand`), `PluginLoader`. Depends on Commands (gets everything transitively).
- **`DumpDetective.DiagnosticScenarios`** — standalone console app used only by the test suite to generate isolated per-scenario heap dumps in a clean child process.
- **`DumpDetective.Tests`** — xUnit integration tests; references Core, Analysis.Memory, Reporting, Commands, Cli directly.

### Key abstractions

- **`ICommand`** — the single registration contract for every command (`Name`, `Description`, `IncludeInFullAnalyze`, `Category`, `Kind` (Memory|Trace), `Run(args)`, `Render(ctx, sink)`). `CommandRegistry` in Cli is the single place commands are registered; `Program.cs` dispatches via `CommandRegistry.Find(args[0])`, and `AnalyzeCommand`/`TraceAnalyzeCommand` iterate `CommandRegistry.FullAnalyzeCommands`. Adding a command means adding one registry entry — not touching a switch statement and a separate hardcoded list.
- **`IRenderSink`** — format-agnostic output abstraction; commands never call `Console.WriteLine` or build HTML strings directly. `SinkFactory` picks the sink from the output file extension; multiple `-o`/`--format` flags fan out via a tee sink.
- **`IHeapObjectConsumer`** — single-responsibility accumulator registered with `HeapWalker.Walk`, called once per live object during the *one* `heap.EnumerateObjects()` pass (parallelized over 8 segment buckets, LPT-scheduled). Adding a new heap metric means adding a new consumer, never editing the walker or adding a second heap walk. `Consume` must not allocate per call (`ConsumeFreeObjects`/`IsThreadSafe` flags control clone-and-merge vs. shared-instance behavior).
- **`ReportDoc`** — polymorphic POCO report tree (`ReportChapter` → `ReportSection` → elements: Table/Alert/Text/KeyValues/CallTree/Gauges/...). This is what `BinSink`/`render`/`diff` serialize and what `ReportDocReplay.Replay(doc, sink)` feeds back through any sink to convert formats. `ReportDiffer.Diff(a, b)` computes element-level deltas for the `diff` command.
- **`HealthScorer`** — pure POCO scoring (`DumpSnapshot` + `ScoringThresholds` → `Findings` + 0–100 score), no ClrMD types, unit-testable without a dump. Thresholds load from `dd-thresholds.json` at repo root (optional; silent fallback to compiled defaults).

### `analyze --full` parallel execution

Runs all `IncludeInFullAnalyze` commands concurrently, each writing into its own `CaptureSink` (in-memory `ReportDoc` capture) using an LPT schedule so slow commands start first. After all finish, the main thread replays every captured `ReportDoc` into the final sink in fixed registry order — output ordering is deterministic regardless of completion order.

### Plugin system

External `.NET` class libraries dropped into `<exe dir>/plugins/` or `~/.dumpdetective/plugins/` are loaded in their own `AssemblyLoadContext`, each implementing `IPluginManifest`/`ICommand`. Plugin commands register alongside built-ins (name conflicts silently favor built-ins) and can opt into `analyze --full --with-plugins` (`ICommand.IncludeInFullAnalyze`) and `trace-analyze --with-plugins` (`ITraceSubAnalyzer`) / `trace-dump-analyze --with-plugins` (`ITraceDumpCorrelationRule`). Plugins can share the host's heap walk via `ICommandHeapContributor` (contribute `IHeapObjectConsumer`s to the single walk instead of triggering a second one) and pin caches across dependent commands via `ICommandCachePin`. See `Docs/Plugins.md` for the full API and `Docs/PluginExample/` for a working example project.

## Conventions worth knowing

- **AOT-safe JSON only.** All serialization goes through `[JsonSerializable]` source-gen contexts in Core — no reflection-based `JsonSerializer.Serialize<T>`, `Type.GetMethod`, `Activator.CreateInstance`, or `Assembly.GetTypes`.
- **Single heap walk.** Never add a second `heap.EnumerateObjects()` call for a new metric — add an `IHeapObjectConsumer` instead.
- **Spectre.Console** for all console output; no `Console.WriteLine` in command code.
- **`DD_DUMP` env var** supplies a default dump path when no positional `.dmp`/`.mdmp` argument is given.
- **`dd-thresholds.json`** (repo root) — optional threshold overrides for `HealthScorer`; missing/invalid file falls back to compiled defaults silently.
- Cache files (`.ddcache/`, `.bfs.idx`, `.parent.map`) are validated against the dump's file size/timestamp on every load and rebuilt automatically if stale — don't assume a present cache file is valid without checking that path.
